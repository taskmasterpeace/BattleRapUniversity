## 1. GAME OVERVIEW

**Genre:** Turn-based, asynchronous **battle rap management sim**.

**Player fantasy (V1):**

* The user plays as a **manager of one battle rapper** (“battler”).
* They join a league, get booked for battles, schedule their preparation days, and then watch simulated battles play out.
* Battles are **numbers + events + text descriptions** (no real bars, no audio).

There is **no human vs human** competition in this first version.
All opponents are **AI-controlled battlers**, and battles are **simulated** based on stats and preparation choices.

## 2. CORE GAME LOOP (WHAT MUST WORK)

The prototype must support this complete loop:

1. **User signs up & creates a battler**

   * Enters a stage name and region.
   * Chooses a primary league (from 2 pre-defined leagues).
   * Picks 1–2 style tags (e.g. “angles”, “comedy”, “gun_bars”).

2. **User is offered battles by a league**

   * System periodically generates AI battle offers for the user’s battler.
   * Each offer specifies:

     * Opponent (AI battler)
     * League
     * Date/time of battle
     * Prep window (days until battle)

3. **User accepts a battle & plans prep**

   * They see a prep calendar leading up to the battle.
   * For each day, they choose **one focus** out of:

     * `research`, `writing`, `performance`, `life`, `rest`
   * Those choices define the battler’s preparation profile.

4. **Battle day: system simulates the battle**

   * At the scheduled time:

     * The system checks prep and no-show conditions.
     * Runs a **segment-based simulation** for 3 rounds:

       * Each round has multiple segments (like “moments” in the round).
       * Some segments are peaks (high scores), some are average or weak.
     * Outputs:

       * Round scores
       * Peak vs average performance
       * Crowd reaction
       * Momentum swings
       * Choke events (if any)
       * Winner

5. **User watches the battle & reads a recap**

   * A **Battle Viewer** screen shows:

     * Round-by-round stats & momentum.
     * Segment timeline with events (haymaker, choke, rebuttal flags).
   * A **Media Feed** shows:

     * System-generated blog-style recap articles (“battle recaps”).
     * Articles are generated from metadata about the battle (not from real bars).

6. **Progression**

   * Battler has:

     * Attributes (writing/performance/personal/resilience)
     * Ranking (rating, wins, losses)
   * Winning/losing battles updates this state.

## 4. DATA MODEL – DATABASE SCHEMA (SUPABASE / POSTGRES)

Implement the following tables with SQL migrations. Use UUID primary keys and `gen_random_uuid()` where appropriate.

### 4.1 profiles

Use Supabase `auth.users` for auth. Create a profile wrapper:

```sql
create table profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text not null,
  created_at timestamptz not null default now()
```

### 4.2 leagues

There are **two leagues** in V1:

* **Small Room Circuit** – 2-minute rounds, more writing-focused.
* **Main Stage Arena** – 3-minute rounds, more performance-focused.

Table:

```sql
create table leagues (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  short_code text not null unique,
  round_length_minutes int not null check (round_length_minutes in (2,3)),
  base_crowd_factor numeric not null,      -- e.g., 0.4, 0.7
  writing_weight numeric not null,         -- 0..1
  performance_weight numeric not null,     -- 0..1
  booking_pace_days int not null,          -- average days between offers
  description text,
  created_at timestamptz not null default now()
);
```

Seed:

* `SMALL_ROOM` – round_length=2, writing_weight > performance_weight.
* `MAIN_STAGE` – round_length=3, performance_weight > writing_weight.

### 4.3 battlers

```sql
create table battlers (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id),
  stage_name text not null,
  region text,
  primary_league_id uuid references leagues(id),
  style_tags jsonb not null default '[]'::jsonb,  -- e.g. ["angles","gun_bars"]
  tier text not null default 'low',               -- 'low','mid','top','god'
  is_ai boolean not null default false,
  created_at timestamptz not null default now()
);
```

* Player-controlled battler = `is_ai = false`, `user_id = auth.user.id`.
* AI battlers = `is_ai = true`, `user_id = null`.

```sql
  public_knowledge int not null default 0,  -- 0..100
```

Values should be in range 1–10 for each attribute.

## 6. SIMULATION ENGINE

Create `/lib/game/simulation.ts` with:

```ts
export async function simulateBattle(battleId: string, options?: { seed?: number }): Promise<void>;
```

### 6.1 Inputs

For a given `battleId`, you must fetch:

* `battle` row (league_id, battler ids, scheduled_at, no_show_player).
* League config.
* Attributes for both battlers.
* Prep blocks for each battler.
* Rankings for each battler.

### 6.2 Prep Profile

For each battler, aggregate:

```ts
type PrepProfile = {
  researchDays: number;
  writingDays: number;
  performanceDays: number;
  lifeDays: number;
  restDays: number;
};
```

Count days by `focus`.

### 6.3 Modify attributes according to prep

Define function:

```ts
function applyPrepModifiers(
  attributes: BattlerAttributes,
  prep: PrepProfile
): ModifiedAttributes;
```

Example behavior (tunable constants):

* Each **writing** day slightly increases writing stats (lyricism, wordplay, creativity).
* Each **research** day improves “angle effectiveness” and “rebuttal chance” (internal modifiers).
* Each **performance** day boosts stage_presence, crowd_control, delivery.
* Each **rest** day boosts resilience slightly.
* Each **life** day helps personal attributes (money, reputation) but doesn’t help battle performance as much.

Clamp final attributes within a reasonable range (e.g., 1–12).

### 6.4 Segment-based round simulation

For each round 1..3:

* Determine `segmentsPerRound`:

  * If `round_length_minutes = 2` → 4 segments.
  * If `round_length_minutes = 3` → 6 segments.

For each battler:

* Compute a **base power**:

```ts
writingPower = weighted average of writing stats
performancePower = weighted average of performance stats

baseScore = writingPower * league.writing_weight + performancePower * league.performance_weight
```

Take resilience and no_show into account:

* No-show → extra penalty to baseScore and higher choke probability.

For each segment:

* Draw a random execution value:

```ts
executionRoll = baseScore + noise(resilience, restDays);
```

Introduce peaks:

* For certain segments, if battler’s `style_tags` + `prep` support it (e.g., `angles` + high research), multiply that segment by a peak factor (~1.15–1.25).

Choke check:

* Based on low resilience, no-show flag, and weak prep (few writing/performance days), sometimes drastically reduce executionRoll (~0.3–0.5x) and mark `choked`.

Record:

* One `battle_segments` row per battler per segment:

  * `segment_score = executionRoll`
  * `event_flags`: e.g. `["haymaker"]`, `["choke"]`, `[]`.

### 6.5 Aggregating round stats

For each battler and round:

* `average_score = mean(segment_scores)`

* `peak_score = max(segment_scores)`

* `consistency_score = inverse of stddev(segment_scores)` (you can store direct stddev and invert in UI).

* `momentum_delta = average_score - opponent_average_score` (store signed).

* `crowd_reaction`:

  * Map average_score to 0..100.
  * Modulate by:

    * league.base_crowd_factor
    * performancePower

* `choked = true` if any segment had choke event.

Create and insert `battle_rounds` rows.

### 6.6 Determine winner & update rankings

* For each round:

  * Compare `average_score` of both battlers.
  * Round winner = higher average_score (with defined tiebreaker).
* Battle winner = battler with most rounds won.
* Update:

  * `battles.winner_battler_id`.
  * Both battlers’ `rankings` rows using a simple ELO-like adjustment.
